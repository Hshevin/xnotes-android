# 保存步骤简化：只让文件保存编码（2026-11-22）

用户要求：旧画布（内容较多的画布）写几笔就提示「无法更新恢复会话」，退出也很卡。简化保存步骤、加快退出；已保存时仍保留恢复备份（用户选择「保留备份、复用已保存字节」），本轮覆盖画布与分页笔记。由主代理规划并编写测试，gpt-6.2-astra 编写实际代码。
状态：讨论完毕，测试已写（未实现，预期 RED）；实现后需 JVM／Robolectric、Android 仪器测试及 MovinkPad Pro 14 真机验证。
本轮边界：分支 `save-slim`（工作树 `tmp/wt-save-slim`）；不打包、不安装、不推送、不发布。

## 现状（master `9ffd2f46`）

一份文档同时有三个写入方，每个都对整份文档做完整编码：

| 写入方 | 触发 | 工作 |
| --- | --- | --- |
| 文件自动保存（`startCanvasWrite` / `startNoteWrite`） | 停笔 1.2 s；暂停/关闭时 flush | 主线程快照 + 完整编码 + 发布 |
| 恢复检查点（`ColdPresentationCoordinator.observe` → `checkpointWorkingSession`） | 每次 `presentationVersion` 变化后 180 ms（每个触摸事件都会触发） | 主线程快照 + 完整编码 + fsync，再整份 `inspectStrict` 与 SHA-256 |
| 工作会话（`submitWorkingSessionIfStable`） | `requestWorkingSession()`（分叉、视图保存等） | 同上 |

`9ffd2f46` 已让暂停时先 flush 文件、再检查点，并对干净文档记 `reopenFromFile`，但检查点仍重新编码备份。结果：

- 写字时每停一下就有一次完整编码（大画布数秒），主线程快照造成卡顿。
- 退出 = 文件编码 + 备份编码 + 回读校验；关闭画布同理（备份随后还被清除）。
- 检查点写入期间内容、视图或保存任务变化 → `stable()`／`current()` 失败 → `failedCheckpoint` 显示「无法更新恢复会话」。这是被新状态超越，而非写入失败。

## 目标与规则

只有**文件保存**会编码文档。恢复备份（working copy）的正文按以下顺序选择来源（每次检查点或工作会话发布都走同一判断）：

1. **复用**：同一模型、同一 `bodyRevision` 且已有已核实的备份 SHA → 只写元数据（现有 `oldSha` 路径）。
2. **复制干净文件**：`cleanCanvasSourceSha()` / `cleanNoteSourceSha()` 非空（已绑定工作区、未修改、来源观察与模型一致、无待确认录音），且不是带 PDF 的笔记（`pdfFile == null`）→ 在会话队列中用 `notebookStorage.openSource(uri, kind)` 取得来源快照，确认 `version.sha256 == cleanSha` 与 `documentId` 一致后，用 `PreparedLegacySessionMutation.prepare*FromEncoded` 把**同一份字节**复制成备份。不编码、不取主线程快照。
   - 来源已变（SHA 或身份不一致）：本次不发布，结果为 `Superseded`（不报错）；该来源观察此后不再用于复制，下一次检查点改走「编码」。
3. **等待文件保存**：文档已绑定自动保存（`canvasAutosaveUri` / `autosaveUri` 等于文档路径、非 `requiresIndependentSave`），有未保存修改，且该文档的去抖或写入任务仍在进行，并且自上次修改后没有失败的保存 → 结果 `Deferred`，不编码、不报错。保存完成（成功或失败）都必须推进 `presentationVersion`，以便观察者重试；成功后走第 2 条，失败后走第 4 条。
4. **编码**：其余情况（未绑定、需独立保存、保存失败、PDF 笔记、来源已变）照旧完整编码。

不变的保证：

- 干净文档仍保留恢复备份，备份字节与已保存文件相同（`CleanColdReopenHostTest` 的备份保留测试继续成立）。
- `prefer-working-copy` 否决标记、`reopenFromFile`、冷启动核对（类型、UUID、位置、SHA-256）、原生 head 保护不变；复制路径同样调用 `trackDiskReopen`。
- 只有本次实际发布并核实的结果才确认备份；来源快照的 SHA 不能代替复制后的核对。
- 带 PDF 的笔记：文件以 `embedPdf=false` 引用共享 PDF，备份目前内嵌 PDF，两者字节不同，本轮继续编码，不复制。
- 不强制提交或取消笔画、选择、文字编辑；笔画中不切换任何保存路径。

## 错误分类

`checkpointWorkingSession` 与 `prepareNativePresentationCheckpoint` 不再只返回 null，而是区分：

```kotlin
internal sealed interface NativeCheckpointResult {
    class Ready(val checkpoint: Editor.PreparedNativePresentationCheckpoint) : NativeCheckpointResult
    data object Deferred : NativeCheckpointResult      // 等待已绑定的文件保存
    data object Superseded : NativeCheckpointResult    // 期间模型/视图/任务/来源变化，稍后重试
    class Failed(val cause: Throwable?) : NativeCheckpointResult  // 实际写入失败（Failed / Changed 之外的发布失败、ProtectedRecovery 另有提示）
}
internal suspend fun Editor.prepareNativePresentationCheckpointResult(homePanes: Set<Pane>, stillCurrent: () -> Boolean): NativeCheckpointResult
```

- 原 `prepareNativePresentationCheckpoint(...)` 保留，返回 `(result as? Ready)?.checkpoint`，现有调用方与测试不变。
- `ColdPresentationCoordinator.checkpoint()`：仅 `Failed`（以及 store 的实际写入失败）调用 `failedCheckpoint` 显示 `err_save_recovery_session`；`Deferred`／`Superseded` 返回 false 且不设消息。`Superseded` 后观察循环须在 `CONTENT_SETTLE_MS` 后自行重试一次（即使 `presentationVersion` 未变）。
- `ProtectedRecovery` 仍显示 `recovery_failed`，语义不变。
- `submitWorkingSessionIfStable` 同样：`Changed`／被新序号超越不显示消息并重新挂起；只有实际失败才显示。

`Editor.presentationContentVersion`（internal，只读）：模型身份、采用序号、文档身份、路径、`bodyRevision`、干净来源 SHA 变化时递增；视口、视图设置、窗格尺寸变化只推进 `presentationVersion`。观察循环比较两次的内容版本选择等待时间。暂停（`onPause`）与离开（departure）的检查点不等待。

## 新接口（测试已按此编写）

平台层（`PreparedLegacySessionMutation.Companion`）：

```kotlin
internal fun prepareNoteFromEncoded(directory: File, encoded: File, expectedSha256: String, ownerToken: Any,
    documentId: String, metadata: SessionStore.Metadata, clearCanvas: Boolean = true,
    fileOps: FileOps = SystemFileOps): PreparedLegacySessionMutation
internal fun prepareCanvasFromEncoded(directory: File, encoded: File, expectedSha256: String, ownerToken: Any,
    documentId: String, metadata: CanvasSessionStore.Metadata, clearNote: Boolean = true,
    fileOps: FileOps = SystemFileOps): PreparedLegacySessionMutation
```

- 准备阶段即把 `encoded` 复制为 `LegacySessionBodyCandidates` 候选（同名规则、fsync），复制时计算 SHA-256；不移动、不修改、不删除 `encoded`（调用方拥有）。
- SHA 不符，或 `BundleReferenceInfo.inspectStrict(候选)` 的类型／`documentId` 不符 → `preparationFailure`；发布返回 `Failed`，不改动任何已有文件，候选清理干净。
- 发布结果的 `LegacyPublication` 为 `bodyFile`=目标、`snapshotOwnerToken`=ownerToken、`bodySha256`=expectedSha256、`documentId`。元数据与清理另一类槽位的行为与 `prepareNote` / `prepareCanvas` 相同，`trackDiskReopen` 同样生效。
